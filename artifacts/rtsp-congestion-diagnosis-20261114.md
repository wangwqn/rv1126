# RTSP拥塞来源：板载对照诊断

## 结论

2026-11-14 21:23～21:35（北京时间）在v1.15.3配置下复现了两类不同来源的背压：

1. 外部网络连接发生TCP丢失恢复、拥塞窗口收缩，触发RTSP客户端队列清理和画面缺口。录像暂停时仍能复现，因此录像不是这类故障的必要条件。
2. 本地录像客户端在重新启动后偶发停读，loopback接收队列堆积且无TCP重传，最后因30秒无文件进度由管理器重启恢复。它是另一个独立的接收管线问题，尚未定位到GStreamer内部具体元素。

不能再把所有主流帧数不足直接归因于录像分片，也不能把仅有背压计数理解为Wi-Fi故障。新的诊断日志已按客户端地址、会话和TCP状态区分来源。

## 来源一：外部TCP网络路径

录像已停止时，21:29:49.270记录：

```text
event=backpressure peer=172.20.10.5:51732 session=da8ac453 stream=0
queued=517737 limit=524288 kernel_outq=78882
unacked=27 lost=27 retrans=1 total_retrans=78
rtt_us=21601 rto_us=893333 cwnd=1 mss=1460
```

`lost=27`是TCP当时标记的丢失报文数；`total_retrans=78`为该连接累计重传，并非当次事件瞬间重传78次。下一包加入将超出512 KiB上限，应用执行背压恢复，清除该客户端的未发送媒体数据，随后等待IDR。

21:29:50.735进入writable恢复，RTO当时已达到1786666微秒。该客户端帧序列出现228004个90 kHz tick的间隔，即2.533秒；180秒实收5327帧。

同阶段Ubuntu接收队列在事件附近为0～少量KB，没有长期堆积的迹象。无线驱动21:29:39～21:29:54的15秒增量为txretrans=264、txfail=20、d11_txnoack=49。说明无线发送可靠性也有实际损失，强RSSI不保证没有重试。

这已将故障定位到外部TCP传输路径，并有无线失败计数支持；尚未通过Windows直接拉流或桥接对照，不能进一步唯一归因于iPhone热点、板端无线驱动、无线干扰或VMware NAT。B阶段外部主/子流在结束时累计TCP重传208/100次，而本地录像连接为0；C阶段累计174/87次。

## 来源二：本地录像接收管线

D阶段恢复录像，21:32:25.075记录：

```text
event=backpressure peer=127.0.0.1:40362 session=452478ff stream=0
queued=323013 limit=524288 kernel_outq=124822
unacked=0 lost=0 retrans=0 total_retrans=0
```

此处queued尚未达到上限，但下一媒体包加入将超过上限。与网络事件不同，该loopback连接没有丢失或重传。

21:32:22的/proc/net/tcp显示录像接收端队列为0x298E50，即2723408字节（约2.60 MiB）；随后录像管理器状态出现：

```text
last_error=recorder made no file progress for 30 seconds
restart_count=1
```

21:32:28新录像连接建立，录像恢复。当前证据明确支持录像进程/其GStreamer接收管线消费停顿，但尚不能区分解复用、时间戳等待、splitmuxsink最终化或磁盘IO。该现象发生于人为恢复录像后的启动阶段，不应直接等同于正式三小时运行期间的所有背压。

D阶段外部视频无相应的大PTS间隔，进一步说明每客户端独立队列可将局部堵塞隔离；本轮日志也没有dropped non-monotonic记录，未证实全局RequestIDR导致其他客户端倒序丢帧的假设。
