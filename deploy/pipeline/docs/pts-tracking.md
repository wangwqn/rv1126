# 主视频PTS匹配与检测间隔跟踪（v1.16.0）

本版本于2026-11-20在本地构建，板载效果与性能待验收。板端此前验证版本仍是
v1.15.3；不能将旧性能报告当作本次修改的真机结论。

## 数据路径与时间边界

```text
RGA2低频RGB → RKNN → DetectionCache（容量8，原始检测PTS/完成时间）
                                ↓ select(main_pts, max_age, wall_ttl)
VENC0输出PTS → 最新PTS通知（容量1） → 同类关联/速度预测
                                ↓ 缩放到旋转后的主流坐标
                            RGA0持久OSD区域
```

主流VENC线程在可能阻塞的RTSP队列之前发布PTS通知。通知只有一个整数，
不持有MEDIA_BUFFER，不新增CPU图像映射，也不等待NPU完成。

这里使用的是**已经输出的主流编码帧PTS**，作为保守的视频时间锚点。OSD作用于
后续RGA处理的帧，区域API仍异步生效；这不是给指定PTS的视频帧原子绑定一组框。
如果以后需要帧级严格同步，应在编码前设计显式帧调度与区域同步，另做时延/吞吐评估。

## 选择与清除规则

1. 选择缓存里最新的`detection.pts_us <= main_pts_us`结果，不使用未来结果。
2. `main_pts_us - detection.pts_us > result_max_pts_ms × 1000`即失效。
3. 从原始NPU完成到当前的单调时间超过`result_ttl_ms`也失效。
4. 显式空检测在对应主视频PTS到达后清除，不越过空结果回退到旧目标。
5. 预测不更新原始完成时间，不把TTL延长。主流PTS通知停止时仍按墙上存活时间清除。
6. PTS倒退、输入尺寸改变、同PTS结果被替换时重置速度，避免沿用错误状态。
7. 主流PTS大跳之后无法匹配到有效结果时清空轨迹，下一次有效检测重新建立。

“完成时间TTL”使用steady_clock，并不是会受NTP调整的系统日历时间。
检查循环无新PTS时最多等待`min(50, result_ttl_ms)`毫秒；实际清框还要加线程调度、
SDK区域调用与硬件在途帧时间，因此不宣称超过阈值后的同一微秒画面立即变化。

## 两次NPU结果之间怎样更新位置

- 每个新结果最多保留100个有效框，按置信度排列。
- 按相同类别、预测位置的IoU、归一化中心距离及尺寸比关联。
- 一个历史目标最多匹配一个新检测，未匹配历史目标立即退休。
- 前两次匹配估计中心速度，后续对速度做平滑，并限制每秒最大位移。
- 在主流PTS上预测框的平移；宽高沿用最近一次NPU观测，整框限制在图像内。
- 首次观测没有速度，保持原框；达到两个有效观测后才开始移动预测。
- 空结果、失效或时间跨度过大都不会继续保留“幽灵轨迹”。

这是低开销的检测关联与运动模型，**不读取中间图像验证运动**。突然转向、急停、
遮挡、同类目标交叉、镜头快速移动时可能预测不准，不等于光流、KCF或ReID。
最大时间差门禁限制了误预测能持续多久，新的NPU结果负责纠偏。
区域/越线事件仍消费真实NPU结果，不把预测框当成新的AI证据生成额外事件。

## OSD开销控制

只有整型框坐标/类别/置信度变化时才调用硬件更新。只移动位置、框宽高和标签未变时，
复用现有BGRA位图，只改区域坐标。类别、置信度、框尺寸或标签上下布局变化时才重绘。
原始NV12视频仍走DMA-BUF/RGA/VENC硬件路径；CPU与RGA区域更新的真机开销需要实测。

## 参数与对照

默认开启，两个时间限制独立，默认均500 ms：

```text
--result-max-pts-ms 500
--result-ttl-ms 500
--no-tracking              只关闭位置预测，保留PTS匹配和超时清除
```

新PTS限制支持1～10000 ms。Web现有TTL配置仍控制完成时间有效期；本次没有往共享
runtime.args强行写入新参数，避免回滚到不认识新选项的旧二进制时无法启动。
如需调整PTS限制，先在独立前台候选中验证参数，不直接改旧版本共用配置。

诊断中的OSD字段：

| 字段 | 含义 |
|---|---|
| pts | 最近处理的主流输出PTS（微秒） |
| age_us | 被选检测与主流PTS的差，无有效选择时为0，不能单凭0判断匹配成功 |
| updates | 实际调用OSD更新的累计次数，包含清框 |
| predicted | 使用非零速度预测的循环次数，不等于新增NPU检测数 |
| expired | 可见框因无法选择有效结果而清空的累计次数，不包含显式空检测 |
| pts_drop | 满队列时被更新PTS替换的通知数，只丢元数据，不是视频丢帧数 |

## 主机验证

```bash
cmake -S deploy/pipeline -B /tmp/rv1126-pts-tracking-host \
  -DRK_VISION_BUILD_DEVICE=OFF -DBUILD_TESTING=ON -DCMAKE_BUILD_TYPE=Debug
cmake --build /tmp/rv1126-pts-tracking-host -j2
(cd /tmp/rv1126-pts-tracking-host && ctest --output-on-failure)
```

旧Ubuntu的CTest不支持`--test-dir`，因此这里显式进入构建目录执行，确保实际发现并运行测试。
共5组：tracking、core、decode、dma_audit、analytics。tracking覆盖历史PTS选择、
多目标独立运动、类别隔离、3 FPS正常间隔、空结果、双重过期、倒退/换尺寸/同PTS替换、
图像边界与无效输入。主机测试不证明硬件区域的真实生效顺序。

## 后续板载验收

通过应用签名OTA部署，保持此前相同模型、码率、AI速率和音频/录像负载。
不刷boot/kernel/rootfs。先做短测，不直接开始24小时测试：

1. 同一场景摆放多个不同类别物体，逐个水平/竖直移动，录像比对检测间隔内的框。
2. 首次出现只应有检测框；两次NPU观测建立后，运动框随主PTS更新，标签类别正确。
3. 目标离场，匹配到空检测后清框；持续遮挡不能无限保留预测。
4. 在独立候选前台进程中用`--ai-delay-ms 1000`模拟慢推理，确认500 ms门禁清除旧框；
   不在正式长期验收中临时修改参数，完成后恢复原配置。
5. 用`--no-tracking`做同负载对照，比较CPU、RSS、FD、DMA、OSD更新和视频PTS缺口。
6. 进行Wi-Fi TCP双流短测，再完成30分钟、3小时回归；逐项记录帧数和解码错误。
7. 同时确认音频、录像、Web与看门狗没有回归，再考虑更长测试。
